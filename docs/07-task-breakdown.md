# 07 开发任务拆解

**版本**：v1.3（2026-11-17）。假设 1–2 名全栈开发，周 = 5 工作日。
拆分原则：每周结束都有可演示物；依赖方向 = 权限 → 组织/赛事 → 报名 → 获奖/证书。

v1.1 变更：新增日志基座、邮箱验证码、身份证加密、赛项/开放组合、公示名单、证书编号计数器等工作项，工期由 12 周增至 15 周（依据见文末「工期影响」）。

**编号约定**：`W1`…`W15` 是**任务包编号，不等于自然周**。一个任务包可以跨多周，多包也可在一周内并行。v1.1 只在 W1、W3、W4、W6、W7、W8 内部增加条目，未重排既有编号——其他文档引用的「W5 快照服务」「W8 交付」仍然有效；压测按当前 W15 执行。里程碑 1 实际占用 11 周，里程碑 2 从 W12 起（即第 12–15 周）。

---

> 本轮确认：单位创建审核仍在 W3；队伍资料审核、团队报名准入与跨届审核上下文保留里程碑 2。原 15 周仅为 v1.1 历史估算，未计入本轮新增内容，实施前重新估时，不将任务包编号当自然周承诺。

## 里程碑 1：单级审核闭环（任务包 W1–W8，约 11 周）

目标：一个真实赛事从创建到证书发放全程可走通（`approval_mode=single`、固定报名表单、无队伍管理——个人报名先行）。

### W1 基础设施 + 账号

- [ ] 中英与主题基座：vue-i18n、Element Plus 中英语言包、浅色/深色/system 语义令牌、首屏偏好恢复；GET/PATCH 用户 locale/theme 与本地缓存同步
- [ ] 工程规范落地：按 CODING_STANDARDS.md 配置格式化、静态检查、pre-commit 与 CI；使用同一套命令
- [ ] backend 初始化：Django 5 + DRF + config 分层 settings（env）、Postgres/Redis/MinIO docker compose 联通
- [ ] **日志基座（v1.1 提前到 W1）**：structlog JSON 输出、`request_id` contextvars 中间件、请求完成日志、SQL 计时 wrapper 与慢查询阈值、脱敏过滤器（DEVELOPMENT.md §2）
- [ ] frontend 初始化：Vite + Vue3 + TS + Element Plus + Pinia + router + axios 拦截器、统一响应/错误码（06 §1）
- [ ] **样式令牌层（v1.1）**：Radix Colors 依赖 + `tokens.css` + Element Plus 变量映射 + 可见边框与响应式基线（FRONTEND_DESIGN_GUIDELINES.md），先立骨架再写页面，否则后期逐页返工
- [ ] `core`：响应包裹、异常处理器、软删除 mixin、分页、审计 middleware 骨架
- [ ] accounts：注册/登录/JWT 轮转/密码重置 + **邮箱验证码**（`verification_codes` 表、同步 SMTP、邮箱/IP 限频、行锁单次消费、试错作废）
- [ ] **SMTP 打通（v1.1，上线前置）**：本地加 Mailpit 容器验证；生产发信域名的 SPF/DKIM 记录清单交运维
- 验收：容器一键起；注册→登录→me 返回 grants 空数组；**任一新接口都能在 stdout 看到带 request_id 的请求日志与 SQL 汇总**

- [ ] rbac app：roles/permissions/user_roles 表 + seed 脚本（6 内置角色 × 02 文档 permission 全清单，含 v1.1 新增 `event:*` / `roster:publish`）
- [ ] `ScopedRolePermission` + `resolve_scope()`（继承规则 1/2/3）+ 单元测试矩阵用例全覆盖
- [ ] `GET /me` 展开 grants；前端 `hasPerm()` + v-perm 指令 + 动态菜单
- [ ] 管理角色授予 API 仅平台管理员可用；普通用户只自动获得本人基础权限
- [ ] `rbac.denied` 埋点接入（403 排障主入口，DEVELOPMENT.md §2.4）
- 验收：测试用例：org_admin 管不了兄弟单位或关联赛事，不能禁用账号/分配角色；赛事创建仅超管；edition reviewer 只能审该届次

### W3 组织与人员

- [ ] orgs：CRUD、**treebeard 物化路径树**（v1.1，取代 parent_id 递归查询）、启停、单位创建申请/平台审核（非自审，通过才建节点）；成员管理 + 主属单位约束
- [ ] profiles：档案完善/修改、人员身份、参赛历史页（数据聚合查询）
- [ ] 证件照：私有桶存储、5MB/格式/2000 万像素校验、重编码剥离 EXIF、本人上传/替换/删除、作用域鉴权与 5 分钟签名预览；对象删除失败重试与孤儿清理
- [ ] **身份证处理（v1.1，P0）**：Fernet 列加解密、pepper 哈希、18 位校验位验证、`uniq_profile_id_number` 查重、末四位展示工具函数、与日志脱敏联调
- [ ] 用户管理后台页（单位管理员仅资料维护；禁用/管理角色分配仅超管可见且后端同样校验）
- 验收：申请人提交"大学→学院"节点创建申请，由另一名平台管理员批准后落库，逐个添加成员（批量人员导入在 W14）、学院管理员只见本树；同一身份证重复绑定被拒，且提示不泄露已有账号信息

### W4 赛事与届次

- [ ] editions：CRUD、时间窗、publish/close、派生状态计算（enrolling 等不入库）
- [ ] **events（v1.1 新增 app）**：赛项 CRUD + 状态、`competition_offerings` 开放组合 CRUD 与停用约束
- [ ] groups：组别（学段）CRUD + 状态 + **资格校验器**（学段/年级/年龄）
- [ ] competition_admins（写 user_roles + 展示表双写）
- [ ] 门户公开页：赛事列表/详情（AllowAny serializer 白名单）
- [ ] 管理端：赛项/组别/开放组合配置页，组合用矩阵视图（一眼看出哪些赛项在哪些学段开放）
- 验收：非管理员视角可浏览已发布赛事与届次；配置 VURC 仅开放大学组后，其他学段的队伍在报名页看不到该赛项

### W5 报名（上）

- [ ] registration_submissions 与快照服务：每次提交保存独立 submission_no、本轮成员/文件与加密表单；current_submission_no 只指向当前提交，驳回后的工作副本不覆盖旧版
- [ ] 唯一索引防重复报名（按 `offering_id` 口径，04 §5）
- [ ] 业务校验全量：时间窗（组合级覆盖）、组合是否开放、赛项人数上下限、教练必填、材料必传、学段相符（42205）、身份证校验位（42206）、邮箱已验证（40104）
- [ ] `eligible-groups` 接口：按队伍/本人学段返回可选组别，杜绝用户自选
- [ ] 敏感信息单独同意、代报授权、监护同意凭据校验；覆盖到每位参赛成员，缺失时不可提交
- [ ] 报名前端表单（个人）：按赛项动态显隐必填与材料上传；需要教练时使用 coach_user_id 关联已注册教练账号，W1 无需队伍管理，服务端校验其 coach 身份与管理范围
- [ ] 埋点 `registration.submitted`（DEVELOPMENT.md §2.4）
- 验收：并发脚本双提交同人同赛项同组别 → 仅一条成功

### W6 报名（下）与单级审核

- [ ] submit/withdraw/resubmit 全链路接 transition() + 带 submission_no 的 approval_records；rejected/org_rejected 可改后重提，已通过可由授权赛事审核员驳回；校验锁定/证书/窗口与旧版本冲突

- [ ] 审核台：筛选列表（届次/赛项/组别/单位/状态）、详情（时间线组件）、approve/reject/return（意见必填）、批量审核

## 工期影响（v1.1）

以下是 v1.1 历史估算（不含 v1.2/v1.3 新增需求）：当时新增 P0 约增加 3 周。最新工期须在任务细化后重估。

| 新增项 | 估时 | 落点 |
| --- | --- | --- |
| 日志基座（structlog + request_id + SQL 计时 + 脱敏） | 3 天 | W1，之后每周复用 |
| 邮箱验证码 + SMTP 打通 | 2 天 | W1 |
| 样式令牌层（Radix + Element Plus 映射 + 响应式） | 1.5 天 | W1 |
| 身份证加解密 + 校验位 + 查重 + 脱敏 | 3 天 | W3 |

**历史估算**：v1.1 将里程碑 1 从 8 周调整为 11 周，总周期从 12 周调整为 15 周；不是本轮新增范围的交付承诺。若必须守住 12 周，砍的顺序建议是 W14 导出中心 → W15 统计图表 → 公示页面前端（接口先留），**不建议压缩日志基座与证件字段分级**：前者决定线上能否排障，后者决定"强制收集身份证"会不会演变成泄露事故。
