# 09 开源项目参考调研

**版本**：v1.1（2026-11-16）
**目的**：确认「综合竞赛管理平台」这一形态是否存在可直接复用或深度借鉴的成熟开源项目，并为各能力点找到最优参考。

> 所有 star 数、许可证、最近推送日期均于 **2026-11-16** 经 GitHub API 核实，非二手转述。

---

## 1. 核心结论（先看这段）

1. **不存在与 CompSphere 同形态的成熟开源项目。** 直接检索 `competition registration system`、`赛事报名管理`、`竞赛管理系统` 命中的几乎全是 0–100 star 的学生课设（如 `zongjixiaoai66/UniversityCompetitionManagementSystem` ★6、`jiaoaodeshaonian1/TurboRace` ★72），无一具备多单位、作用域权限、届次隔离、审核留痕这套结构。**自研业务模型是必要的，不是重复造轮子。**
2. **真正的成熟方案在相邻领域**：活动票务报名（pretix / eventyay / Attendize / Hi.Events）、学术会议投稿评审（indico / OpenCFP）、竞赛引擎（CTFd / Hydro / 青大 OJ）。它们各自解决了 CompSphere 的某一片，没有一家解决全部。
3. **最关键的可借鉴对象是 indico**（CERN，MIT，★2128，活跃）：它的「会议 → 届次（event occurrence）→ 投稿 → 多角色评审 → 决议」链路，与 CompSphere 的「赛事 → 届次 → 报名 → 审核 → 获奖名单」几乎同构，且许可允许直接读码借鉴。**建议投入最多阅读时间。**
4. **CompSphere 最独特、也最没有现成答案的地方是 RBAC 作用域模型**（02 文档的 `(user, role, scope_type, scope_id)` + org 树继承）。Casbin 的 `RBAC with domains` 概念最接近，但只有单层 domain，不支持四层嵌套 + 树继承。**自研 `ScopedRolePermission` 的判断成立**（详见 §3.1）。
5. **许可证是本次调研最硬的约束**：pretix、Hi.Events、Hydro、certo、edubadges 全部 **AGPL-3.0**；Attendize 是自定义的 Attribution Assurance License。对可能闭源交付学校/企业的 CompSphere 来说，这些**只能读、不能抄代码**（详见 §2）。

## 3. 分能力点对标

### 3.1 RBAC 作用域 + 组织树（02 文档 / W2，全系统地基）

| 候选 | 许可 | 与 02 文档的差距 | 可用性判断 |
| --- | --- | --- | --- |
| **apache/casbin** ★20500 | Apache-2.0 | 官方支持 7 种访问模型，其中 **"RBAC with domains/tenants：用户可在不同 domain 持有不同角色集"**——与 `scope_type` 思路一致。但 domain 是**扁平单层**，02 文档要求 `global ⊇ org ⊇ competition ⊇ edition` 四层 + org 子树继承，Casbin 需自建多层 policy 拼装 | 读它的 `rbac_model_with_domains.conf` 建模思路；**不建议引入 Casbin**（Go 内核 + PyPI 绑定层，为一个 60 项权限清单加一层策略引擎不值得，且 W2 要的是可单测的纯 Python `resolve_scope()`） |
| **dfunckt/django-rules** ★1978 | MIT | 谓词式授权、**不入库**，与 02 文档"角色为数据驱动、可自定义并勾选权限子集"直接冲突（PRD §2.2 明确要求自定义角色存表） | 概念可参考；注意有**两个同名仓库**——`maraujop/django-rules`（★151，2023-11 停更）是原始版，`dfunckt` 才是维护版，别引错 |
| **django-guardian** ★3921 | BSD 风格（API 返回 NOASSERTION） | 解决**逐对象**授权，不是**作用域**授权。用它实现 02 文档要为每个 edition/competition/org 建大量 ObjectPermission，性能与维护都差 | ❌ 不适合本模型 |
| **keycloak/keycloak** ★37890 | Apache-2.0 | 有 realm/client/组角色体系，但 Java 全家桶 + 独立部署，与 PRD「单机 Docker Compose、99.5% 可用、1–2 名全栈开发」的约束完全不匹配 | ❌ 过度设计 |
| **django-treebeard** ★1226 / **django-mptt** ★2965 / **django-treenode** ★805 | Apache-2.0 / BSD / MIT | 三者都解决 `organizations.parent_id` 的树查询（04 文档）。02 文档 §4 规则 2「org 作用域覆盖该组织的下级组织树」需要**高效子树查询**，裸 `parent_id` 递归在 PostgreSQL 上要写 recursive CTE | ✅ **推荐 django-treebeard**（Apache-2.0、活跃、Materialized Tree 模式读子树是单条查询，正合"权限解析高频、组织树低频变更"的场景） |

**结论**：`ScopedRolePermission` **自研判断成立**，没有任何库能免改满足 02 文档。但组织树这一层应该用 `django-treebeard`，不要手写递归——这是 04 文档目前没提、W2/W3 会踩的点。

### 3.3 证书生成 + 公开验证（PRD §3.7 / W8，CompSphere 独有卖点）

| 候选 | 许可 | 判断 |
| --- | --- | --- |

### 3.6 竞赛引擎（PRD §1 明确"不做"，但仍记录以免误判）

CTFd ★6912（Apache-2.0，Flask）、hydro-dev/Hydro ★7236（AGPL）、QingdaoU/OnlineJudge ★6559（MIT，**Django 3.2 + DRF + Vue**，2024-10 后停更）。

这三者是"比赛本身怎么跑"（题目、判题、排行、对抗）的成熟答案。CompSphere 定位为**管理平台而非比赛引擎**（PRD §1、决策 #1），故**不属于借鉴范围**。但 QingdaoU/OnlineJudge 作为 Django+DRF+Vue 的中型单体样本，其 **app 划分与 Docker 编排**对 05 文档 §2 的模块化单体落地有一点结构参考价值——仅此而已，注意它已停更两年、Django 3.2 已 EOL。

## 6. 调研方法与局限

**方法**：GitHub REST API（`search/repositories` + `repos/{owner}/{repo}` + `repos/{o}/{r}/license`）拿元数据；对每条许可结论**读取 LICENSE 原文**而非信任 API 的 `spdx_id` 字段（本次多个 AGPL 项目 API 返回的正是 `NOASSERTION`，只看该字段会误判）；对 indico / eventyay / CTFd / OnlineJudge 的结论读取 **README 原文**核实能力描述，不凭印象。全程在 GitHub 官方 API 上完成，未使用搜索引擎二手信息。

**局限（重要，勿过度信任本文结论）**：

1. **未做源码级审查**。所有「值得借鉴什么」的判断来自 README、LICENSE、元数据与项目公开定位，**没有逐文件读实现代码**。indico/pretix 的流程细节仍需按 §4 时间预算实读验证。
2. **中文项目检索覆盖不足**。GitHub 搜索对中文标题/描述的召回明显弱于英文，且国内同类系统大量以闭源 SaaS 存在（各类"竞赛管理系统"商业产品），**不代表国内没有可参考实现**，只代表公开可检索到的成熟开源实现很少。若需要国内商业产品的功能面参照，应另行调研其官网/招投标文件。
3. **快照性质**。star 数、活跃度、许可均为 **2026-11-16** 当日状态；Hi.Events 的强制署名条款、eventyay 的授权链等属于**法律解释问题**，本文给出风险提示但不构成法律意见。若本项目将商用分发，`AGPL` 相关判断建议请法务确认。
4. **匿名/登录态额度限制**：本轮在已认证的 GitHub API（core 5000/时、search 30/分）下完成，但多关键词组合查询会因 AND 语义返回 0 条；已对空结果改用点名核实，仍可能有**未被检索命中的相关项目**。

- **必读 indico**（MIT）：唯一在"多角色投稿-评审-决议"上和 CompSphere 同构且许可干净的成熟项目。
- **pretix 值得认真读但一行代码都不能抄**（AGPL）；**Hi.Events / Attendize 直接排除**（强制署名 / 停更+许可模糊）；**eventyay 标称 Apache 但血统可疑，按 AGPL 对待**。
- **基础设施不要自己写**：`django-import-export`（BSD）、`django-treebeard`（Apache）、`WeasyPrint`（BSD）、MIT 的 Element Plus 脚手架。
- **RBAC 作用域必须自研**，Casbin 只借建模思路，`drf-access` 这个依赖名是错的（02 文档待修）。
- **Open Badges 规范该读一页**，它把"证书撤销后公开页怎么表现"这个你们还没定死的问题讲清楚了。
