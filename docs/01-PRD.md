# 01 产品需求文档（PRD）

**产品名**：竞云（综合竞赛管理平台，CompSphere）
**版本**：v1.7（2026-11-18）
**范围**：第一版 = 里程碑 1 + 里程碑 2，本文档描述完整第一版需求；里程碑拆分见 [07-开发任务拆解](07-task-breakdown.md)。

> v1.4：本场冻结/未审取消、队号与赛项身份、证件更正审核、护照及无邮箱代建登录；规则见 §3–5。

## 1. 产品定位

面向学校、企业、协会及赛事主办方的竞赛**管理平台**（非比赛引擎）。第一版核心价值：让平台为不同单位创建赛事并指定人员管理，让参赛人员完成报名，让管理员完成审核与证书发放。

首期为集中部署的一套生产系统，平台统一运维、各单位按作用域协作，不做单位独立品牌、域名或独立运营实例。首期验收覆盖真实赛事的组织、队伍、报名、单级审核与公示闭环；证书移至下一期，不作为首期硬性要求。无固定上线日期，任务依赖和验收门槛见 [07](07-task-breakdown.md)。

首个落地场景是 VEX 机器人赛事体系（赛项 VURC / V5RC / VIQRC / VAIMRC / VGORC，学段 ES / MS / HS / U）。模型不与该赛事绑定：赛项与组别都是届次下的配置数据，换其他机器人竞赛或学科竞赛只改配置、不改表结构。

**不做**（P2/永久排除出第一版）：复杂赛程编排、对阵树、实时比分、晋级算法、在线评分、支付、短信、第三方身份认证。

## 2. 角色与组织模型

### 2.1 两个正交概念

- **人员身份**（profile level）：一个人在业务上是什么——队员、教练、（管理员兼有的）工作人员。存于 `user_profiles.person_type`。
- **管理角色**（permission level）：一个人在系统里能做什么。存于 `user_roles`，带**作用域**：全局 / 某单位 / 某赛事 / 某届次。

一个人 = 1 个账号 + 1 个人员档案 + N 条组织成员关系 + N 条（角色, 作用域）记录。例如：张三是 A 大学的教练（人员身份），同时是赛事 E 的赛事管理员（角色 @ scope=赛事 E），不需要两个账号。

### 2.2 系统内置角色

| 角色 code | 名称 | 典型作用域 | 主要职责 |
| --- | --- | --- | --- |
| `platform_admin` | 平台超级管理员 | 全局 | 管理所有组织、用户、角色、系统配置 |
| `org_admin` | 单位管理员 | 单位 | 管理本单位人员、队伍、报名信息 |
| `competition_admin` | 主办方管理员/赛事管理员 | 赛事或届次 | 管理已授权赛事/届次的配置、审核、获奖名单与证书；不创建赛事 |
| `reviewer` | 审核员 | 届次 | 仅负责所分配届次的报名审核 |
| `team_coach` | 教练 | 单位 | 查看本单位队伍，代报本人负责队伍；队伍资料与成员由单位管理员统一管理 |
| `participant` | 队员 | 无（仅本人） | 维护个人信息、报名、查看结果、下载证书 |

角色为**数据驱动**（`roles` 表），不写死在代码枚举里；上述 6 个为 seed 数据，平台管理员可自定义新角色并配置权限集（第一版允许自定义角色，但权限项从固定 permission 列表中选择）。

### 2.3 组织类型与层级

支持类型：`school` 学校、`college` 学院、`enterprise` 企业、`association` 协会、`host` 主办单位、`organizer` 承办单位、`other` 其他。

组织为**可配置父子树**（treebeard `path` 物化路径，父级由 API 解析），不强制全平台单一大树：

```
平台
├── 主办单位 A ── 承办单位 B / 合作企业 C
├── 某某大学 ── 计算机学院 / 自动化学院
└── 某某企业
```

两种关系严格区分：

- **成员关系**：用户属于哪个单位（`organization_members`，含身份：学生/教师/员工等）。
- **赛事角色关系**：某单位在某赛事中是主办/承办/协办/赞助（`competition_organizations.role_type`，挂在赛事上而非届次上，届次可覆盖）。

## 3. 功能模块需求

### 3.1 用户与人员管理（P0）

统一账号与档案，人员身份和管理角色分离。

- 自助注册使用邮箱验证码；经审核单位的管理员可代建普通学生账户，不强制学生邮箱。代建记录创建人/单位及授权或监护同意凭据，初始随机密码只交付一次，首次登录强制修改；不能拿证件号本身作密码。
- 登录支持「证件类型 + 签发国 + 号码 + 密码」，也保留已绑定邮箱 + 密码。身份证默认 CN，护照须选择签发国；号码只放 HTTPS 请求体，所有错误统一，不作为日志/URL/username。证件登录不代表完成实名认证。
- 参赛成员绑定身份证或护照其中一种，不强制身份证；纯教练/工作人员可不绑定。当前每份证件只绑定一个账户；身份证与护照不能自动识别为同一人，重复身份争议由管理员核验，不能宣称系统能自动防住一人多证。
- 首次绑定校验格式；已绑定证件的号码、类型或签发国更改均走申请，所属单位管理员或平台审核，禁止申请人及证件所属人自审。单位管理员只能处理本单位普通成员，管理账户/跨单位争议由平台处理。批准前旧证件有效；批准事务内核验版本与新号唯一性，切换绑定、释放旧号、使旧会话失效，历史快照不改。
- 有已验证邮箱可自助找回；有当前有效主属单位的普通学生账户，也可由该单位管理员核验后重置，不区分代建/自助注册或是否绑定邮箱。转移完成后权限随当前主属单位切换，原代建单位不保留重置权。无归属单位且无法自助找回时，邮件联系平台管理员核验处理，不凭邮件内容直接重置。重置强制首次改密、撤销旧会话、留审计并通知；单位管理员不得重置管理账户，代建接口不得覆盖既有账户密码。
- 档案含姓名、性别、出生日期、证件照、学号/工号、单位、身份、学段/年级、职务；邮箱可空，手机号可共用，报名联系人由提交人/监护人/教练提供，不必是学生个人联系方式。账号禁用、管理角色分配仅平台管理员。
- 证件照默认选填，JPEG/PNG、≤ 5MB、建议 3:4；私有桶存储，本人或 profile:read 作用域内人员读取，公示和队友信息不展示。
- 支持中文/英文及浅色/深色/跟随系统，偏好存账号并本地缓存。系统邮件仅发往已验证邮箱，无邮箱用户使用站内通知；代报提交人接收其负责报名的通知。
- 固定模板的学生账号、队伍与成员导入纳入首期：预览校验、逐行报错，通过原有权限及业务审核后才生效，禁止覆盖既有账号凭据或绕过成员唯一归属。任意 Excel 智能识别、完整导入导出中心和整库历史迁移不在首期范围。专业字段不采集，权限与导出范围见 02。

### 3.2 队伍管理（首期基础能力）

首期包含建队、资料/成员维护与审核、赛季许可、团队报名、成员唯一归属及历史留痕。复杂跨队特批在里程碑 2 实现；未支持的操作明确阻止，禁止靠直接修改数据库处理。下述特批规则保留为后续契约，不代表首期开放特批入口。

- 本单位全部队伍由单位管理员统一管理，包括创建、修改名称、配置教练/队长、成员入退队及解散；创建和资料/成员修改均走申请审核，教练不具有这些管理写权限。创建及赛季激活申请仅平台审核；资料/成员修改由另一名有权单位管理员或平台审核，申请人不能自审；不因管理员提交而跳过审核。单位须已通过创建审核且正常启用。普通变更不迁移所属单位，跨单位转移另行设计。
- 创建审核通过才建立可用队伍；修改待审时保留原已审核版本，只有通过后才更新正式资料和成员关系；已提交赛事报名仅保留当时快照，不跟随队伍档案更新。每次申请保存完整加密提案、基于的已审核版本、意见与审核人；退回/驳回不覆盖旧版，可复制为新申请重提。
- 队伍独立于赛事，team_id 为稳定身份，对应「队号 × 稳定赛项类型」；队号在平台内只能归属一个单位，同号不同赛项为不同队伍。编号/赛项/归属构成身份，普通修改不迁移这些字段；新建同名队伍不会继承历史或准入资格。每次报名固定使用当时已审核版本和成员快照，后续改人/改名不回写已提交报名。
- 一名学生全平台同时只能属于一支当前队伍（队号×赛项），不同赛项也不能同时入队。本人可自主退队，立即结束当前归属并留历史；单位管理员发起的普通入退队仍须变更审核生效。回到上一次退出的队伍走普通入队审核，不必平台特批；仍校验其他有效参赛绑定，不能借多次退队绕过限制。
- 同赛季同赛项首次报名审核通过时建立学生→队伍绑定，跨组别共用。自主退队、报名驳回/取消、队伍解散均不删除绑定；赛季归档后不再限制未来入队，历史仍保留。已绑定学生在同赛季不能普通加入同赛项其他队伍，单位管理员不能放行。
- 学生可单独向平台管理员申请特批换队，记录来源/目标队伍、涉及届次、理由与审核结果；平台批准并执行入队，不能同时属于两队。所有相关未归档赛季绑定均须核对，不因只选一届绕过其他限制；平台申请禁止自审。
- 特批换队先检查原/目标队伍涉及的报名：含该学生的原队待审或已通过报名须按授权更正流程取消或驳回，重提时排除该学生；名单锁定或存在非作废证书则先解锁/作废。目标队伍已提交的报名不自动加人，仍须取消或驳回后重提，时间窗不自动延长。绑定及当前归属原子切换、旧版快照不改写，全部操作留审计。
- 本场队员只能从当时已审核且当前未退出的队伍成员中按赛项规则选择；新增/替换队伍成员先走队伍变更审核。修改本场已通过的成员选择也须先驳回再重提。
- 队伍资料审核、赛事准入和本场报名审核是独立条件；晋级资格跟随队伍，但须记录产生资格的学生阵容，后续轮次按该阵容核对；成员替换仅平台特批，单位档案改人不自动继承晋级参赛资格。

待审单位/队伍/证件申请在尚无审核决定时可主动「取消并修改」：原申请标 withdrawn 并保留提案，原子复制为关联的新草稿；已审核申请不能走此路径，驳回后可新建关联草稿重提。

### 3.3 单位管理（P0）

- 单位 CRUD、类型、上下级、状态（正常/停用）。
- 单位管理员更换由平台管理员撤销旧授权并授予新授权，立即失效旧权限缓存并记录授权审计；不建立离职档案。单位成员关系只表达平台归属，不作为人事履历。
- 平台管理员分配单位管理员；成员管理（加入/移除/身份变更/批量导入）。
- 单位参赛记录与获奖统计。
- 单位创建（含平台后台发起）先提交申请，由平台管理员审核，申请人不能自审；通过后才建立正式单位、组织树节点与成员关系，退回/驳回留痕，可新建申请重提。单位成员加入审批仍是独立流程，org:approve_join 不能用于批准新单位。

### 3.3.1 学生单位转移（P0）

- 账号归学生本人保留：转学、升学不新建账号，不更改证件登录、历史报名或证书；每名学生最多一个有效主属单位，附属关系不能获得密码重置权。
- 学生或经授权的单位管理员发起申请，取得学生本人/监护人确认 → 原单位同意转出 → 新单位确认接收。新单位接收时同一事务结束旧主属关系、追加新关系并递增 affiliation_version，切换资料/重置权限并失效旧会话及授权缓存；交接期间原关系仍有效，拒绝/取消不改变归属。
- 原单位无法处理或有争议，由平台管理员核验后代办转出并说明理由，新单位仍须确认接收；申请人/学生本人不审核自己的交接，双方处理人分离。不能通过普通成员添加、档案 PATCH 或证件号查询直接接管已有学生。
- 转单位不自动转队。仍有当前队伍时须先退出，赛季队伍绑定与晋级资格不变；跨队参赛仍走平台特批。原/新单位分别只保留提交时属于自己的历史范围，新单位不因此获得旧单位的历史附件、证件和内部意见。

### 3.4 赛事管理（P0）

**队伍赛季注册（首期）**：队伍稳定身份仍为队号×赛项，每赛季另有注册许可。首次创建由平台管理员审核，并在同一事务建立队伍及该赛季许可；已有队伍进入新赛季由单位管理员申请激活，仅平台管理员审核，禁止自审。许可不跨赛季继承，待审/驳回/撤销均不得报名；未审可取消，驳回后可修改重提，保留原申请及审核记录。资料与成员变更仍走既有单位审核，不自动撤销赛季许可，报名快照独立冻结。提交/重提/审批通过均核对赛事所属赛季的有效许可，再校验单场准入、成员资格和时间窗；撤销许可不改写历史，存量待审报名须恢复许可或驳回，已通过报名另走更正流程。新提交/重提仅当前 active 赛季，切换后旧赛季待审可继续审核，但不得借重提新增参赛。

**赛季（season）**：例如 2026–2027，平台配置名称、起止日期及 draft/active/archived 状态，可跨自然年；年份标签不用于推算日期。一个赛季包含多场赛事，具体举办场次（现有 edition）必须归属一个赛季。competition 仅作为跨赛季复用的赛事系列资料。界面显示“赛季 → 赛事 → 赛项/组别 → 报名”，不要求用户理解系列与场次表。

- 平台仅有一个当前赛季，由平台管理员显式切换到 active 赛季；普通用户和单位/赛事管理员只读显示当前赛季，不能通过页面、URL 或 API 改变它。无当前赛季时显示未开放并禁止新报名。切换不迁移队伍许可、不归档旧赛季、不改写旧报名；原赛季待审事项仍由授权管理端处理。历史入口独立授权，不使用“切换当前赛季”浏览历史。赛季归档前须结束其未完成赛事与待审报名；归档后禁止新报名、重提与审批通过，日期到期不自动切换或归档。
- 防串队与晋级阵容约束以“season_id × 稳定赛项 × 学生”生效，覆盖同赛季所有赛事和组别；参加另一场比赛、关闭单场赛事或转单位不释放绑定，只有赛季归档后才不再阻止未来入队。报名、奖项、证书和审核仍按具体赛事场次隔离。

**赛事（competition）**：名称、简介、封面、分类（学科/科技/创新创业/…）、级别（校级/省级/国家级/国际）、主办/承办/协办单位（多个、每种角色多个）、章程与附件、状态机（见 03 文档）、管理员分配。

**届次（edition）**：一个赛事多届（"2026 第一届"、"2027 第二届"），届次承载全部业务时间线与数据：报名时间窗、活动时间、赛项、组别、开放组合、报名、获奖、证书、统计、公示设置。**所有业务数据挂届次，不挂赛事。**

### 3.5 赛项与组别管理（P0）

**赛项与组别是并列的两个维度**，一条报名 = 一个赛项 + 一个组别（如「V5RC 高中组」）。这不是把一件事拆成两处：赛项回答「比什么、怎么组队」，组别回答「和谁一起比」，二者各自独立被用于评奖、公示、名额与统计。

**赛项（event，挂届次）**——由机器人平台/项目决定，承载实际约束：

| 配置 | 字段 |
| --- | --- |
| 赛项编码 | `code`：`VURC` / `V5RC` / `VIQRC` / `VAIMRC` / `VGORC` / 自定义 |
| 名称 | `name`（"VEX V5 机器人竞赛"）、`short_name` |
| 队伍人数 | `min_members` / `max_members`（VEX 通常 2-3 人，平台决定规模） |
| 指导教师 | `coach_required`（VEX 各赛项普遍要求） |
| 报名材料 | `material_requirements`（JSON：材料名、是否必传、格式、大小上限） |
| 报名费用 | `fee`（第一版仅记录展示，不在线支付） |
| 说明 | `description`、`robot_kind`（仅用于分组展示，不参与校验） |
| 状态 | 启用 / 关闭 |

**组别（group，挂届次）**——学段，只承载资格规则：

| 配置 | 字段 |
| --- | --- |
| 组别编码 | `code`：`ES` 小学 / `MS` 中学 / `HS` 高中 / `U` 大学 / 自定义 |
| 名称 | `name`（"高中组"） |
| 对应学段 | `school_level`（与人员档案、队伍学段比对的字段；NULL = 不限，供非按学段划分的赛事使用） |
| 报名类型 | `enrollment_type`：个人 / 团队 / 两者皆可 |
| 年龄限制 | 首期不配置或自动校验；`age_min` / `age_max` 仅保留为后续设计字段 |
| 年级限制 | `grade_limits`（JSON 数组，空 = 不限；学段之下的细化） |
| 状态 | 启用 / 关闭 |

**开放组合（offering）**：赛项与组别的笛卡尔积**不全部成立**——VURC 只设大学组，VEX GO 只设小学组。因此届次显式声明开放哪些组合（`competition_offerings`），并可在组合上覆盖名额与报名起止时间。报名、奖项、获奖名单、公示名单一律以「届次 × 赛项 × 组别」为单位。

**取消专业限制（v1.1）**：机器人竞赛按学段分组，不按专业限制参赛资格。`major_limits` 与人员档案 `major` 均删除，不再采集或导入专业字段。

**本场学段由提交人选择**：按赛事开放组合选择学段/组别并随本轮报名冻结；不按全队最高学段自动推导。声明须与所选组别一致，仍校验年级及成员要求，审核员结合在读证明人工核验；首期不按出生日期计算年龄资格。档案 school_level 只作资料参考。在读证明通过原业务表单上传至私有存储，由有权审核人员查看原件，不交给 AI 识别或读取。

**表单口径（决策 #7）**：第一版报名表字段固定（姓名、联系方式、单位、身份、年级、材料附件），赛项差异通过"附件要求 + 人数与教练约束"实现；动态表单引擎为 P1。

### 3.5a 通过名单公示（P0，v1.1 新增）

参赛者、教练与单位需要能查到"谁通过了审核"，这是赛事公开性与单位核对报名信息的基础需求。

- **届次级开关** `roster_publication`：`open` 完全公开 / `login` 需登录可见 / `none` 不公示，默认 `open`。
- **需主办方主动发布**：开关为 `open` 但未点「发布名单」（`roster_published_at` 为空）时不对外显示，防止审核中途被外部看到半截数据。
- **公示内容**：队号、单位名称、赛项、组别、成员姓名、（若已评奖）奖项。成员身份、联系方式、身份证号一律不公示，服务端按字段白名单 `roster_publish_fields` 过滤（04 §4）。
- **公示范围**：审核状态为 `approved` 的报名；名单进入 `confirmed` 后补充获奖信息。
- **可见性判定顺序与被驳回方的处理**见 02 §4.7（`login` 档存在匿名越权风险，已单列）。
- 入口：门户公开页按 赛事 → 届次 → 赛项 → 组别 逐层下钻，队伍卡片可直接查看成员。

### 3.5b 队伍准入（里程碑 2，赛事可配置）

- 每届选择 open（符合资格的队伍均可报名）或 allowlist（仅指定队伍）；高级别赛事可显式选 allowlist，不按级别自动推断。allowlist 模式只开放团队报名，避免个人通道绕过。
- 主办方管理员导入或手动维护本届准入名单，以「队号 + 赛项」匹配 team_id；不得按名称自动匹配。重复、未知编号进入错误清单，先人工确认/注册审核队伍，再重新导入；预览确认后事务写入，不隐式创建队伍或覆盖队员。
- 进入名单仅表示有报名资格，不代表队伍资料审核或本场报名审核通过；原有时间窗、人数、学段、材料校验照常执行。晋级资格跟随该队伍身份，队伍档案以后获批换人不丢资格；每场已提交报名的阵容独立冻结，不能直接随档案变更。
- 提交/重提时在事务内复核当前准入；移除队伍不自动改写存量报名，待审记录提示准入已失效，批准前须恢复准入或驳回；已通过报名的更正另走审核员驳回流程。名单变更留审计并清理资格缓存，名单不公开全量。

### 3.6 报名与审核管理（P0）

流程：选赛事/届次 → 选本场赛项、学段/组别（提交人选择）→ 填信息传材料 → 提交 → 审核 → 通过 / 退回修改 / 驳回。

- 报名主体支持**个人**（`individual_user_id`）与**队伍**（`team_id`）两种，由组别 `enrollment_type` 约束；团队报名保存成员快照。
- 校验：报名时间窗（组合级可覆盖届次窗口）、赛项与组别状态、组合是否开放、学段与年级资格、赛项人数上下限、教练必填、必传材料、所选证件格式（身份证校验位或护照规则）、账户已完成必需资料与首次改密、同一主体在同一「赛项 × 组别」下不重复报名。
- 学段一致性：本场声明 selected_school_level 须与所选组别匹配（42205）；不拿队伍档案派生学段代替用户选择。团队的稳定赛项类型须与本场赛项匹配。
- 审核：**届次级配置** `approval_mode` = `single`（赛事审核）/ `two_stage`（单位初审 + 赛事复审）。里程碑 1 只交付 `single`；`two_stage` 的状态机已预留（见 03 文档）。
- 审核操作：通过、驳回（本轮不通过，可修改重提）、退回修改（可重提）、审核意见必填（驳回/退回时）、批量审核、审核记录全留痕。
- 已有报名后，不直接覆盖影响资格或审核的组别、人数与必交材料规则；变更须保留版本、说明对存量报名的影响并通知受影响用户，不静默改写冻结快照。一般说明和场地可修改并留痕。
- 通知：站内消息 + 已验证邮箱的异步邮件；任务与业务同事务写入 outbox，失败补投，不把提交成功等同于邮件送达。
- 关键通知覆盖提交、审核结果、退回及重要赛事变更；无邮箱学生保留站内消息，队伍事务同时通知有权负责的教练或单位管理员。邮件送达不等于用户已读；短信及微信通知留待后续。
- 名单：按届次/赛项/组别/单位/状态筛选，导出 Excel。
- 本场资料自 submit 起冻结（含选定队员、声明学段、材料与审核模式）。未发生本轮审核决定时，提交人可 cancel_review 回到可编辑草稿；原提交标记取消并留档，下次提交新增轮次。单位初审已通过、或本场已 approved 时不能主动取消，须先由审核员驳回。
- 已通过报名需要更正时，由本届赛事审核员/赛事管理员执行「驳回」（意见必填），再由原有编辑权人修改重提；获奖名单已锁定或关联证书未作废时禁止驳回。操作使报名转为 rejected 并退出通过名单，重提按当前资格/准入重新校验，并将届次当前审核模式冻结到新轮次；每一轮提交资料与文件引用不可变且可对照查看。直接修改队伍/个人档案不改变任何已提交版本。
- 审核工作台（团队历史上下文在里程碑 2）并列「本场提交资料」「队伍资料版本」「历届参赛记录」：历史按报名编号和提交轮次展示赛事/年度、赛项/组别、各轮结果/奖项与当届队员姓名、角色、学段、年级，并可比较人员变化；读取已提交报名快照，不用当前成员名单重建历史。历史队员不要求仍在队。跨赛事历史仅为当前队伍的只读最小摘要，不返回历史附件、联系方式、证件、照片和内部审核意见。

### 3.7 获奖名单（首期）与证书管理（里程碑 2）

- 奖项仅奖励参赛学生，支持个人或团队参赛成果；不设单位奖、组织奖和教练奖，团队证书仅发给该轮冻结的学生队员。
- 奖项配置挂**届次 × 赛项 × 组别**（通用奖项可不绑定具体组合）：等级（一等/二等/三等/优秀…）、名称、排序、获奖名额（软限制）。
- 获奖名单：手动录入（从**已通过报名**中选择，杜绝孤儿记录）或 Excel 导入；名单以「赛项 × 组别」为单位各自走状态机。
- **导入匹配规则（决策 #10）**：导入模板以报名编号 `batch_no` 为主匹配键；姓名 + 证件类型/签发国/号码作为二次校验列，仅在必要时收集并加密暂存，冲突行进"待人工确认"列表，不自动写入。
- 名单审核：名单整体提交 → 主办方负责人确认（状态机见 03），确认后锁定。
- 证书：批量生成（Celery 异步 PDF）、编号规则 `CS-{届次前缀}-{5位序号}`（如 `CS-0012-00345`；序号取自届次独立计数器，一经签发永久不变，不随届次主键或数据迁移变化，见 04 §6）、二维码指向公开验证页（验证页仅展示证书编号、持有人姓名脱敏、赛事/赛项/组别/奖项、签发日期与有效性）、补发（作废旧证生成新证）、作废。
- **作废证书在验证页的去向**（v1.1 补定）：已补发的旧证验证页显示「已作废」并给出新证编号，避免持证人已下载的 PDF 变成死链；未补发的纯作废只显示「已作废」。规则见 03 §6.1。
- 团队获奖按已提交报名中冻结的参赛成员逐人发证，教练不获奖或发证；个人报名同样一人一张。获奖记录固定引用具体审核通过的 submission_no，证书成员外键必须来自同一轮；唯一约束为「获奖记录 × 该轮报名成员」至多一张非作废证书，队伍后续换人不影响收件人。

### 3.8 系统管理与统计（P0 基础 / P1 完整）

- 平台看板：用户数、单位数、赛事/届次数、报名人数、审核通过率、获奖人数（P0 做计数卡片，P1 做图表与多维统计）。
- 单位/组别维度报名统计、导出（P1）。
- 操作日志 `audit_logs`（P0 记录关键写操作：审核、名单变更、证书操作、角色变更、导出）。
- 自动备份、校验、告警与人工恢复为首期必需能力；恢复目标、覆盖范围和演练见 [部署指南](../docker/README.md#3-一致性备份与恢复)。

## 4. 全局业务规则

1. **快照原则**：报名提交时冻结成员名单与人员关键信息副本；队伍后续改人不回溯已提交报名。
2. **届次隔离**：任何查询/统计/配置默认以届次为边界。
3. **软删除**：日常业务删除使用 `is_deleted` + `deleted_at`，历史不能通过普通 CRUD 硬删除；受控个人信息处置另按 §5 审定的留存与删除规则执行，不能以软删除代替必要删除。
4. **状态驱动**：所有状态迁移集中在服务层校验（见 03 文档状态机），禁止绕过状态机直接 update。
5. **时区**：全部存 UTC，展示 Asia/Shanghai；时间窗判定以 UTC 存储值为准。

## 5. 合规与个人信息保护

- 参赛成员仅选择一种当前证件：身份证或护照；按身份核验用途说明并取得敏感信息单独同意。代建/代报须记录授权，不满 14 周岁须有监护人同意凭据；文案上线前法务审定。
- 首期不开发线上监护人身份核验或签署流程，单位在系统外取得必要授权并负责核验；系统记录私有凭据引用、范围与核验人，不能自动声称已取得授权。真实资料入场前确定可接受的凭据形式及核验要求。
- 证件号码应用层 Fernet 加密；匹配用 HMAC-SHA256(DOC_HASH_PEPPER, 类型|签发国|规范化号码)。API/日志最多末四位，不返回完整号码、密文或哈希；护照同样处理。
- 已批准更正可以释放旧证件，当前绑定唯一；申请审核前不释放，历史报名/证书不随之改写。注销不自动释放当前绑定，身份争议由管理员核验。
- 报名、获奖等赛事个人明细仅 competition_admin（本赛事）与 platform_admin 可导出；全局人员明细仅平台。单位管理员只看权限内资料/汇总，不导出个人明细；导出与敏感操作写审计。
- 已发布公示只读字段白名单（队号、单位、赛项、组别、姓名、奖项）；不展示证件、联系方式、照片、出生日期。证书公开验证保留最小有效性结果。
- 届次 closed 后保留全部历史，普通门户、公示、本人报名/队伍业务历史不再返回；有 registration:read_history 的管理人员按原范围读取，单位管理人员仅本单位记录。公开证书真伪验证保持独立最小接口，不提供完整赛事历史。
- 密码 Argon2；初始/重置密码只交付一次并强制改密，手机号和未验证邮箱不作身份凭据。删除请求与历史留存冲突按人工核验及法务政策处理。
- 不开放自助注销；业务资料按用途长期保存，平台保留受控更正、停用及必要删除请求的处理机制。证件唯一绑定只用于防重复账号，不构成全部资料永久不可删除的依据。证件、报名快照、授权凭据及审核历史分别制定期限与处置责任；实际采集前审定政策，备份 30 天不等于业务资料保存期限。

## 6. 非功能需求

- 并发：报名截止前 1 小时高峰，按 500 并发提交、P95 < 800ms 设计（Redis 限流 + Celery 削峰为 P1 手段，第一版保证接口幂等与数据库约束兜底）。
- 幂等：报名提交、证书生成接口幂等（唯一约束 + 幂等键）。
- 文件：单材料 ≤ 20MB，类型白名单，存 MinIO/S3，私有桶 + 签名 URL。
- 可用性目标 99.5%（单机 Docker Compose 部署规模下）。
- 邮件送达：注册与找回密码依赖邮箱验证码，需独立配置发信域名 SPF/DKIM，否则验证码邮件进垃圾箱等于注册不可用；该项是 P0 上线前置条件（05 §3.1、docker/README）。
- 移动端：学生和教练可完成全部日常任务；管理端可查看及处理单条事务，复杂赛事配置、批量导入及批量审核面向桌面，手机入口明确提示适用设备。首期采用响应式网页，不另做 App。

## 8. 当前关键决策（v1.4）

单位/队伍资料审核与赛事报名审核分离；晋级跟随队号+赛项身份；每场提交冻结，未审可取消修改，驳回可重提；学段人工选择；证件更正经管理员审核后释放旧号；企业可代建无邮箱账户；closed 历史仅管理端可见。

## 9. 待决事项

后续能力：新增 AI 悬浮助手需求，支持在本人授权范围内查询赛事、辅助报名及审核，复用业务组件与校验；不是里程碑 1 已交付能力。交互、数据处理未决项和接入验收见 [11-AI 助手设计](11-ai-assistant.md)。

1. **个人信息处置细则**：长期保存、无自助注销，保留受控更正/停用和必要删除机制；分类型期限、处理责任及历史完整性冲突口径须在实际采集前审定（§5）。
2. **上线合规审定**：敏感信息单独同意、线下授权凭据与核验要求、证件绑定及历史资料留存处置政策，按 §5 已确认工程规则准备材料，由平台负责人交法务审定。公示范围已定为仅通过者，未通过者不公开。
