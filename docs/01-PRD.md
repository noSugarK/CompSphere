# 01 产品需求文档（PRD）

**产品名**：竞云（综合竞赛管理平台，CompSphere）
**版本**：v1.0（2026-11-16）
**范围**：第一版 = 里程碑 1 + 里程碑 2，本文档描述完整第一版需求；里程碑拆分见 [07-开发任务拆解](07-task-breakdown.md)。

---

## 1. 产品定位

面向学校、企业、协会及赛事主办方的竞赛**管理平台**（非比赛引擎）。第一版核心价值：让不同单位能创建和管理赛事，让参赛人员完成报名，让管理员完成审核与证书发放。

**不做**（P2/永久排除出第一版）：复杂赛程编排、对阵树、实时比分、晋级算法、在线评分、支付、短信、第三方身份认证。

## 2. 角色与组织模型

### 2.1 两个正交概念

- **人员身份**（profile level）：一个人在业务上是什么——队员、教练、（管理员兼有的）工作人员。存于 `user_profiles.person_type`。
- **管理角色**（permission level）：一个人在系统里能做什么。存于 `user_roles`，带**作用域**：全局 / 某单位 / 某赛事 / 某届次。

一个人 = 1 个账号 + 1 个人员档案 + N 条组织成员关系 + N 条（角色, 作用域）记录。例如：张三是 A 大学的教练（人员身份），同时是赛事 E 的赛事管理员（角色 @ scope=赛事 E），不需要两个账号。

### 2.2 系统内置角色

| 角色 code | 名称 | 典型作用域 | 主要职责 |
| --- | --- | --- | --- |
| `platform_admin` | 平台超级管理员 | 全局 | 管理所有组织、用户、角色、系统配置 |
| `org_admin` | 单位管理员 | 单位 | 管理本单位人员、队伍、报名信息 |
| `competition_admin` | 主办方管理员/赛事管理员 | 届次 | 创建与管理赛事、组别、审核、获奖名单、证书 |
| `reviewer` | 审核员 | 届次 | 仅负责所分配届次的报名审核 |
| `team_coach` | 教练 | 单位 | 管理所属队伍与队员、代为报名 |
| `participant` | 队员 | 无（仅本人） | 维护个人信息、报名、查看结果、下载证书 |

角色为**数据驱动**（`roles` 表），不写死在代码枚举里；上述 6 个为 seed 数据，平台管理员可自定义新角色并配置权限集（第一版允许自定义角色，但权限项从固定 permission 列表中选择）。

### 2.3 组织类型与层级

支持类型：`school` 学校、`college` 学院、`enterprise` 企业、`association` 协会、`host` 主办单位、`organizer` 承办单位、`other` 其他。

组织为**可配置父子树**（`organizations.parent_id`），不强制全平台单一大树：

```
平台
├── 主办单位 A ── 承办单位 B / 合作企业 C
├── 某某大学 ── 计算机学院 / 自动化学院
└── 某某企业
```

两种关系严格区分：

- **成员关系**：用户属于哪个单位（`organization_members`，含身份：学生/教师/员工等）。
- **赛事角色关系**：某单位在某赛事中是主办/承办/协办/赞助（`competition_organizations.role_type`，挂在赛事上而非届次上，届次可覆盖）。

## 3. 功能模块需求

### 3.1 用户与人员管理（P0）

统一人员档案，不为队员/教练分建用户体系。

- 注册（手机号/邮箱 + 验证码）、登录（JWT）、找回密码、账号启用/禁用。
- 人员档案：基本信息（姓名、性别、头像、出生日期）、联系信息（手机号、邮箱）、身份信息（身份证号、学号/工号，**按需收集**，见 §5 合规）、所属单位、人员身份、附加信息（专业、年级、职务）。
- 批量导入/导出（Excel，P1 起做导入，P0 做导出）。
- 用户角色分配（平台管理员、单位管理员在本单位内）。
- 参赛历史查询（按人聚合届次、报名、获奖）。

### 3.2 队伍管理（P1）

- 创建/编辑队伍（名称、编号、所属单位、指导教练、队长、状态）。
- 添加/移除队员（记录变更历史，见 §4 快照原则）。
- 查看队伍参赛历史。
- 队伍独立于赛事存在，可跨届复用，每届报名成员可不同。

### 3.3 单位管理（P0）

- 单位 CRUD、类型、上下级、状态（正常/停用）。
- 单位管理员分配、成员管理（加入/移除/身份变更/批量导入）。
- 单位参赛记录与获奖统计。
- 组织入驻申请与平台审批（第一版：平台管理员后台创建 + 申请流程简化为"申请-审核"两步）。

### 3.4 赛事管理（P0）

**赛事（competition）**：名称、简介、封面、分类（学科/科技/创新创业/…）、级别（校级/省级/国家级/国际）、主办/承办/协办单位（多个、每种角色多个）、章程与附件、状态机（见 03 文档）、管理员分配。

**届次（edition）**：一个赛事多届（"2026 第一届"、"2027 第二届"），届次承载全部业务时间线与数据：报名时间窗、活动时间、组别、报名、获奖、证书、统计。**所有业务数据挂届次，不挂赛事。**

### 3.5 组别管理（P0）

组别挂届次。配置项：

| 配置 | 字段 |
| --- | --- |
| 组别名称 | `name`（本科组/研究生组/高职组/企业组…） |
| 报名类型 | `enrollment_type`：个人 / 团队 / 两者皆可 |
| 参赛对象 | `target_audience`：多选（学生/教师/企业人员…） |
| 年级限制 | `grade_limits`（JSON 数组，空 = 不限） |
| 专业限制 | `major_limits`（JSON，第一版仅存储与校验提示，不做复杂规则） |
| 队伍人数 | `min_members` / `max_members`（个人组为 1/1） |
| 指导教师 | `coach_required` 布尔 |
| 报名材料 | `material_requirements`（JSON：材料名、是否必传、格式、大小上限） |
| 报名费用 | `fee`（第一版仅记录展示，不在线支付） |
| 状态 | 启用 / 关闭 |

**表单口径（决策 #7）**：第一版报名表字段固定（姓名、联系方式、单位、身份、年级、专业、材料附件），组别差异通过"附件要求 + 必填项开关"实现；动态表单引擎为 P1。

### 3.6 报名与审核管理（P0）

流程：选赛事/届次 → 选组别 → 填信息传材料 → 提交 → 审核 → 通过 / 退回修改 / 驳回。

- 报名主体支持**个人**（`individual_user_id`）与**队伍**（`team_id`）两种，由组别 `enrollment_type` 约束；团队报名保存成员快照。
- 校验：时间窗、组别状态、参赛对象/年级限制、人数上下限、必传材料、每人每届次每组别不重复报名。
- 审核：**届次级配置** `approval_mode` = `single`（赛事审核）/ `two_stage`（单位初审 + 赛事复审）。里程碑 1 只交付 `single`；`two_stage` 的状态机已预留（见 03 文档）。
- 审核操作：通过、驳回（终止）、退回修改（可改后重提）、审核意见必填（驳回/退回时）、批量审核、审核记录全留痕。
- 通知：站内消息 + Celery 邮件（审核结果、退回提醒）。
- 名单：按届次/组别/单位/状态筛选，导出 Excel。

### 3.7 获奖名单与证书管理（P0）

- 奖项配置挂届次 × 组别：等级（一等/二等/三等/优秀…）、名称、排序、获奖名额（软限制）。
- 获奖名单：手动录入（从**已通过报名**中选择，杜绝孤儿记录）或 Excel 导入。
- **导入匹配规则（决策 #10）**：导入模板以报名流水号 `batch_no` 为主匹配键；姓名 + 身份证号作为二次校验列，冲突行进"待人工确认"列表，不自动写入。
- 名单审核：名单整体提交 → 主办方负责人确认（状态机见 03），确认后锁定。
- 证书：批量生成（Celery 异步 PDF）、编号规则 `CS-{届次ID四位补零}-{序号}`（如 `CS-0012-00345`）、二维码指向公开验证页（验证页仅展示证书编号、持有人姓名脱敏、赛事/组别/奖项、签发日期与有效性，不暴露身份证等敏感信息）、补发（作废旧证生成新证）、作废。
- 一人一获奖记录对应一张有效证书（唯一约束防重复）。

### 3.8 系统管理与统计（P0 基础 / P1 完整）

- 平台看板：用户数、单位数、赛事/届次数、报名人数、审核通过率、获奖人数（P0 做计数卡片，P1 做图表与多维统计）。
- 单位/组别维度报名统计、导出（P1）。
- 操作日志 `audit_logs`（P0 记录关键写操作：审核、名单变更、证书操作、角色变更、导出）。
- 数据备份方案见部署文档。

## 4. 全局业务规则

1. **快照原则**：报名提交时冻结成员名单与人员关键信息副本；队伍后续改人不回溯已提交报名。
2. **届次隔离**：任何查询/统计/配置默认以届次为边界。
3. **软删除**：业务实体统一 `is_deleted` + `deleted_at`，不做物理删除（证书、审核记录永久保留）。
4. **状态驱动**：所有状态迁移集中在服务层校验（见 03 文档状态机），禁止绕过状态机直接 update。
5. **时区**：全部存 UTC，展示 Asia/Shanghai；时间窗判定以 UTC 存储值为准。

## 5. 合规与个人信息保护

面向学校收集身份证号、手机号、学生信息，需满足《个人信息保护法》最小必要原则：

- 身份证号等敏感字段**按组别材料要求按需收集**，组别未要求则报名表不出现该字段。
- 收集页面明示用途（报名审核/证书签发），变更用途需重新同意（第一版：字段级 `consent` 勾选记录在报名快照中）。
- 导出功能仅对 `competition_admin`（本赛事）与 `platform_admin` 开放，且导出行为写 `audit_logs`（含导出字段清单）。
- 公开页面（证书验证）仅输出最小信息且姓名脱敏。
- 密码 Argon2/bcrypt 哈希；手机号/身份证号数据库列加密为 P1 评估项（至少保证日志与错误信息不落敏感明文）。

## 6. 非功能需求

- 并发：报名截止前 1 小时高峰，按 500 并发提交、P95 < 800ms 设计（Redis 限流 + Celery 削峰为 P1 手段，第一版保证接口幂等与数据库约束兜底）。
- 幂等：报名提交、证书生成接口幂等（唯一约束 + 幂等键）。
- 文件：单材料 ≤ 20MB，类型白名单，存 MinIO/S3，私有桶 + 签名 URL。
- 可用性目标 99.5%（单机 Docker Compose 部署规模下）。

## 7. 范围优先级总表

| 优先级 | 内容 |
| --- | --- |
| **P0（里程碑 1）** | 账号与人员档案、组织与成员、角色权限（含作用域）、赛事/届次/组别、报名（固定表单）、单级审核 + 状态机、奖项与获奖名单（手动 + batch_no 导入）、证书生成与验证页、站内/邮件通知、基础看板、审计日志 |
| **P0 末尾或里程碑 2** | 队伍管理、两级审核（`two_stage`）、Excel 完整导入导出、名单审核锁定、证书补发/作废、统计图表 |
| **P1** | 动态报名表单、组织参赛统计、敏感字段加密评估、导出中心 |
| **P2（不做）** | 赛程/对阵/实时成绩/评分/支付/短信/第三方认证 |

> 注意修正了原方案两处范围矛盾：动态表单原列 P0 流程依赖、通知原出现在 P0 但邮件在 P2 ——现统一为"固定表单进 P0、邮件通知进 P0、动态表单与短信进 P1/P2"。
