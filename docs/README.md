## 关键设计决策记录（ADR 摘要）

1. **定位收窄**：第一版不做赛程编排、对阵、实时比分、晋级算法、在线评分。
2. **角色与组织身份分离**：`users` + `user_profiles`（人员身份：队员/教练）与 `roles`（管理角色：单位管理员/赛事管理员等）两套体系，一个人可同时持有多身份多角色，不需要多账号。
3. **赛项与组别并列建模**（v1.1 取代原「组别独立建模」）：赛项（比什么、怎么组队）与组别（和谁一起比）是届次下两个正交维度，实际约束在赛项、资格规则在组别；报名/奖项/名单/公示以「届次 × 赛项 × 组别」为单位。
4. **只开放合法组合**（v1.1）：赛项与组别的笛卡尔积不全部成立（VURC 仅大学组），由 `competition_offerings` 显式声明，非法组合在数据库层无法写入。
5. **一切业务数据挂届次**：报名、获奖名单、证书、统计均关联 `competition_editions`（届次），不直接关联 `competitions`，保证多届数据天然隔离。
6. **提交版本不可变**：每次重提新建 submission_no，已通过可由审核员驳回后修改重提，旧提交及其成员/文件保留。

   **报名成员快照分双列**（v1.1 细化）：`registration_members` 同时保存完整加密 `snapshot_enc` 与脱敏 `public_info`；公示与队友查看只读后者，白名单过滤发生在数据库读取层而非 Python 层。
7. **队伍学段派生而非自选**（v1.1）：一队只属一个组别，学段由成员档案派生（混合年龄队取最高学段），报名界面不提供自选组别入口。
8. **审核先做单级**：里程碑 1 只实现"赛事审核"；两级审核（单位初审 + 赛事复审）作为届次级配置在里程碑 2 加入，两种模式共用同一套状态机。
9. **静态报名表单**：里程碑 1 采用固定字段 + 各赛项不同的附件/人数/教练约束；动态表单引擎为 P1。
10. **注册只走邮箱验证码**（v1.1）：短信在 P2 未实现，原「手机号/邮箱验证码」不可落地；手机号改为必填联系字段但不验证真伪，因此不得作为身份凭证。
11. **身份证号强制收集 + P0 列加密**（v1.1，反转原「按需收集 / P1 加密」）：证件号是身份核验、防重复报名、证书签发三件事的共同依据；配套唯一约束 `uniq_profile_id_number` 才真正防住一人多号。
12. **通知 = 站内消息 + Celery 发业务邮件；验证码同步 SMTP**：短信、第三方认证为 P2。
13. **模块化单体**，不用微服务；按 Django app 划分模块边界。
14. **获奖导入匹配规则**（v1.1 调整）：以报名编号 `registration.batch_no` 为主键关联；身份证因必填而可稳定作为二次校验列，仍不靠姓名匹配。
15. **证书编号一经签发永久不变**（v1.1）：序号取自届次独立计数器，不依赖自增主键、不回收，数据迁移与届次合并都不改写历史编号。
16. **日志埋点是 P0 交付项而非运维附加**（v1.1）：请求、SQL、Celery 任务的耗时与错误全量结构化输出，凭 `request_id` 可还原一次线上故障。

17. **创建与资料审核**：单位创建由平台审核；队伍创建/修改由单位管理员审核、平台代审，禁止自审；待审修改沿用旧审核版本。
18. **赛事队伍准入**：本届 open/allowlist，准入不替代报名审核；审核上下文可看该队跨届最小历史摘要与历史队员。队伍相关能力仍在里程碑 2。
